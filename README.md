# Inception

Secure WordPress infrastructure deployment using Docker Compose on Alpine Linux,
extended with four bonus services.

## Description

Inception is a system administration project that consists of setting up a small
infrastructure of containerized services, following strict rules: one service per
container, custom-built images, TLS-only web access, persistent named volumes, and
secrets kept out of the repository.

The stack is composed of **seven services**, each built from its own Dockerfile
based on **Alpine 3.23** (the penultimate stable release, as of 2026-11-17).
All images are tagged `:inception`; the `latest` tag is never used.

### Mandatory services

| Service | Role | Exposure |
|---|---|---|
| **nginx** | The only web entrypoint. Serves HTTPS with TLSv1.2/TLSv1.3 only, using a self-signed certificate generated at container startup. Serves static files and proxies PHP via FastCGI. | port **443** |
| **wordpress** | WordPress + PHP-FPM 8.3 (no nginx inside). Downloaded, configured and installed automatically on first startup using WP-CLI, including the creation of two users. | internal 9000 |
| **mariadb** | Database server (no nginx inside). Database, application user and root password provisioned from environment variables and Docker secrets. | internal 3306 |

### Bonus services

| Service | Role | Exposure |
|---|---|---|
| **redis** | Object cache for WordPress through the *Redis Object Cache* plugin and the PhpRedis extension. Reduces MariaDB queries. Authenticated with a Docker secret. | internal 6379 |
| **ftp** | Pure-FTPd server jailed in the WordPress volume, allowing file management over FTP. PureDB virtual user, anonymous logins disabled. | ports **21** + **30000-30009** |
| **adminer** | Single-file database administration UI in its own container with a dedicated PHP-FPM. Requires MariaDB credentials. | HTTPS **8443** |
| **static** | Showcase site generated by Hugo in a multi-stage build. The runtime image contains only nginx and the generated HTML/CSS — no Hugo, no PHP. | HTTPS **8444** |

### Architecture

```
Browser ─HTTPS:443──┐
Browser ─HTTPS:8443─┤─► nginx ─┬─ FastCGI:9000 ─► wordpress ─┬─ TCP:3306 ─► mariadb
Browser ─HTTPS:8444─┘          │                             └─ TCP:6379 ─► redis
                               ├─ FastCGI:9000 ─► adminer
                               └─ HTTP:80 ──────► static (nginx + Hugo output)

FTP client ─:21 + :30000-30009─► ftp (Pure-FTPd)

Volumes:  wp_data ── wordpress (rw), nginx (ro), ftp (rw)
          db_data ── mariadb (rw)

Docker network: inception (user-defined bridge)
```

### Main design choices

- **Alpine over Debian**: minimal footprint and no "magic" init helpers — every
  daemon (`nginx`, `php-fpm83`, `mariadbd`, `redis-server`, `pure-ftpd`) runs
  explicitly in the foreground as PID 1, with no hacky keep-alive loops.
- **Automated, idempotent provisioning**: entrypoint scripts only provision on
  fresh volumes, so restarts never wipe data. WordPress waits for MariaDB to
  accept connections before installing, avoiding startup races.
- **Secrets**: all passwords live in `secrets/*.txt`, mounted as Docker secrets at
  `/run/secrets/`, and are git-ignored. Only non-sensitive configuration is stored
  in `srcs/.env`.
- **Persistence**: two Docker named volumes (`db_data`, `wp_data`). The Docker
  daemon's `data-root` is redirected so their data physically lives in
  `/home/vde-maga/data` on the host, while remaining true named volumes.
- **Runtime DNS resolution in nginx**: `fastcgi_pass` and `proxy_pass` use a
  variable plus `resolver 127.0.0.11`, so nginx starts and survives even when an
  upstream container is down, instead of dying with `host not found in upstream`.
- **Build-time tools stay out of runtime images**: Hugo runs in a builder stage;
  the static image ships only nginx and the generated files.
- **Cache without a volume**: Redis is a pure object cache (`save ""`,
  `appendonly no`, `allkeys-lru`), so persistence is deliberately disabled and no
  volume is needed.
- **Resilience**: every service uses `restart: unless-stopped`.
- **No `latest` tag**: all images are tagged `:inception`.

Each service directory contains a `Dockerfile` and, where applicable,
configuration files in `conf/` and an entrypoint script in `tools/`. Services whose
daemon needs no runtime preparation (Adminer, static) use the binary directly as
`ENTRYPOINT`, so the daemon is PID 1 with no shell wrapper at all.

### Alpine-specific challenges solved

Choosing Alpine meant solving problems that Debian-based setups never encounter.
All of these were diagnosed from logs and fixed hands-on:

| Symptom | Cause | Solution |
|---|---|---|
| `env: can't execute 'php'` | Alpine names binaries by version (`php83`) | symlink `php → php83`, only in the WordPress image where WP-CLI's shebang needs it |
| `Extracting a zip file requires ZipArchive` | PHP extensions are separate packages | `php83-zip` |
| `Call to undefined function ctype_digit()` | `ctype` is built into PHP on Debian, separate on Alpine | `php83-ctype` |
| `Allowed memory size exhausted` during WordPress download | conservative default `memory_limit` | custom `php.ini` with `memory_limit = 256M` |
| MariaDB provisioning client could not connect | `MYSQL_HOST` forces TCP, but the temporary server runs `--skip-networking` | `unset MYSQL_HOST` during provisioning |
| `Access denied` for the database user | trailing newline in secret files became part of the password | `tr -d '\n'` when reading secrets |
| `host not found in upstream "wordpress"` | nginx resolves literal upstream names at startup | `resolver` + variable in `fastcgi_pass` / `proxy_pass` |
| vsftpd `500 OOPS` and PAM issues in containers | seccomp sandbox, writable chroot, PAM dependency | chose **Pure-FTPd** with PureDB virtual users instead |
| pure-ftpd: `Invalid argument: " #login"` | inline comment after a line-continuation `\` — the backslash escapes the space, so the comment text is passed as an argument | comments on their own lines; `\` must be the last character of the line |
| `pure-ftpwho` unavailable | Alpine build lacks `--with-ftpwho` | observe sessions with `docker top ftp` |

### Virtual Machines vs Docker

Virtual machines emulate physical hardware. A VM runs its own kernel and full OS,
with a fixed amount of resources allocated from the host. This provides strong
isolation, at the cost of overhead and slower startup.

Docker containers virtualize user-space only. They share the host's kernel and
resources, making them lightweight and fast to start, with process-level
isolation instead of hardware-level isolation. In this project, the whole stack
runs inside a VM, and each service runs in its own container.

### Secrets vs Environment Variables

Environment variables are convenient for non-sensitive configuration (domain
name, database name, usernames). However, they are visible via `docker inspect`
and process environments, so they are not appropriate for credentials.

Docker secrets are mounted as files inside the container (`/run/secrets/<name>`)
only for the services that declare them. They are never baked into images or
Dockerfiles. In this project, `.env` holds configuration, while all passwords —
including the Redis and FTP ones — are read from secrets at runtime.

### Docker Network vs Host Network

A user-defined bridge network provides container-to-container communication with
built-in DNS resolution (containers reach each other by service name), isolated
from the host. Inbound access requires explicit port publishing: nginx publishes
443 for the mandatory web stack, plus 8443 and 8444 for bonus services, and the
FTP server publishes 21 with a fixed passive range. The bonus section of the
subject explicitly allows these additional ports.

The host network removes isolation: containers share the host's network stack
directly. It can improve performance but exposes every listening port and is
forbidden by the subject. This project uses a dedicated bridge network named
`inception`.

### Docker Volumes vs Bind Mounts

Volumes are managed by Docker. They are abstracted from the host filesystem
layout, portable, and managed with Docker tooling (`docker volume ...`).

Bind mounts map an arbitrary host path into a container. They are useful for
development, but couple the container to the host's filesystem and let containers
modify host files directly. The subject forbids bind mounts for persistent
storage: this project uses named volumes, with the daemon's `data-root`
relocated to `/home/vde-maga/data` to satisfy the required data location.

## Instructions

### Requirements

- A Linux virtual machine (this project was developed on Alpine 3.23)
- [Docker Engine](https://docs.docker.com/engine/install/) and
  [Docker Compose v2](https://docs.docker.com/compose/install/)
- `make`, `git`, `openssl`

### Steps

1. Clone the repository:

```sh
git clone https://github.com/vde-maga/42-inception.git
cd 42-inception
```

2. Configure the VM (once):

- Set Docker's `data-root` to `/home/vde-maga/data` in `/etc/docker/daemon.json`
  and restart Docker.
- Add `127.0.0.1 vde-maga.42.fr` to `/etc/hosts`.

*See [DEV_DOC.md](DEV_DOC.md) for detailed commands.*

3. Review `srcs/.env` (non-sensitive configuration only):

```dotenv
DOMAIN_NAME=vde-maga.42.fr
MYSQL_DATABASE=wordpress
MYSQL_USER=wpuser
MYSQL_HOST=mariadb
WP_TITLE=Inception
WP_ADMIN_USER=vde-maga
WP_USER=carolina

REDIS_HOST=redis
REDIS_PORT=6379

FTP_USER=ftpuser
FTP_PASV_ADDRESS=127.0.0.1
FTP_PASV_MIN=30000
FTP_PASV_MAX=30009
```

4. Create the secret files in `secrets/` (git-ignored):

- `db_password.txt` — MariaDB application user password
- `db_root_password.txt` — MariaDB root password
- `credentials.txt` — WordPress users password
- `redis_password.txt` — Redis `requirepass`
- `ftp_password.txt` — FTP virtual user password

*Example: `openssl rand -base64 24 > secrets/db_password.txt`*

5. Build and start:

```sh
make
```

The website is available at `https://vde-maga.42.fr` (from inside the VM).
The certificate is self-signed, so the browser will show a warning — this is
expected. See [USER_DOC.md](USER_DOC.md) for usage details.

**AI usage**

An AI assistant was used throughout the project as a guided tutor and pair
debugger, specifically for:

- planning the architecture and the order of implementation;
- drafting first versions of Dockerfiles, entrypoint scripts and the Compose file;
- debugging Alpine-specific issues (versioned PHP binary names, missing `zip` and
  `ctype` extensions, PHP memory limits, MariaDB socket-vs-TCP initialization,
  trailing newlines in secret files, startup race conditions between services,
  nginx upstream DNS resolution, and a shell line-continuation parsing bug);
- choosing between alternatives (Pure-FTPd over vsftpd, Hugo multi-stage over a
  development server);
- drafting this documentation and the user/developer docs.

All AI-generated content was applied incrementally, executed in the VM, reviewed
and corrected where needed. Several suggestions were wrong and were fixed through
testing — for example, `docker kill` does not trigger restart policies because
Docker treats it as a manual stop, which was verified experimentally. Every
component of the project was verified hands-on and can be explained and modified
during the evaluation.
